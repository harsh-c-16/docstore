## Sanity checks

| Check | Result | Pass |
|---|---|---|
| bloom-on `readmissing` clearly faster than bloom-off | 3,511,899 vs 104,510 reads/s: 33.6x faster (991,654 of 999,960 bloom checks skipped the read: 0.83% false positives, theory 0.82%) | yes |
| `find_indexed` examines far fewer docs than `find_collscan` | 93 vs 1,000,000 documents examined for the same kind of query: 10,753x fewer; p50 latency 1.19 ms vs 1.63 s | yes |

## Observations

- `overwrite` and `fillrandom` show the cost of the two-level LSM (DESIGN.md D16): random keys
  overlap every L1 file, so each compaction rewrites almost all of L1. Write amplification over
  fill + overwrite is 9.05, and when compaction falls behind, L0 reaches the slowdown trigger and
  writes sleep 1 ms (p99 ~1.07 ms; 17.18 s of stall in the overwrite run). Leveled compaction is
  the fix (future work).
- `readrandom` is bound by block reads: the 8 MiB block cache holds ~4% of the ~216 MB of data
  (963,158 misses for 1,000,000 reads), so most reads cost a `pread` of a 4 KiB block plus its
  CRC check.
- `fillrandom (sync=1)` is one `fdatasync` per write: 1.53 ms median on this drive. Group commit
  (future work) would share one fsync between concurrent writers.

## How to reproduce

```bash
scripts/run_benchmarks.sh 1000000
# which runs, each on an empty database directory:
./build/release/docstore_bench --benchmarks=fillseq,readrandom,readmissing,readwhilewriting,scan --num=1000000 --bloom_bits=10 --db=<dir>
./build/release/docstore_bench --benchmarks=fillseq,readmissing --num=1000000 --bloom_bits=0 --db=<dir>
./build/release/docstore_bench --benchmarks=fillrandom --num=1000000 --db=<dir>
./build/release/docstore_bench --benchmarks=fillrandom --num=10000 --sync=1 --db=<dir>
./build/release/docstore_bench --benchmarks=overwrite --num=1000000 --db=<dir>
./build/release/docstore_bench --benchmarks=doc_insert,find_collscan,find_indexed --num=1000000 --db=<dir>
```
